The scan starts at the top-left of the screen and walks forward one byte at a time. Each press of “Next byte” is one spi_valid && !spi_busy handshake in the RTL. The right side shows, in wiring order, how that byte is computed. Click anywhere on the screen to jump the scanner there.

96 × 64 · 8×8 cells · 12 columns × 8 rows
Speed

After you change the state or the text, the screen does not change at once: new pixels are written only when the scanner reaches them. Same as the real panel, which shows the last pixels it received.

How the counters move after a handshake always_ff, only on the handshake cycle

  • WIN and cnt < 5 → cnt + 1
  • WIN and cnt == 5 → enter PIX, x = y = 0, lo = 0
  • PIX and lo == 0 → lo = 1 (high byte just sent)
  • PIX and lo == 1 and x < 95 → x + 1, lo = 0
  • PIX and lo == 1 and x == 95 and y < 63 → x = 0, y + 1, lo = 0
  • PIX and lo == 1 and x == 95 and y == 63 → back to WIN, cnt = 0 (end of frame)

A pixel counts as written only on the cycle its low byte is sent. One frame = 6 window bytes + 96 × 64 × 2 = 12294 bytes.

Three things to watch for

The counters are in charge. oled_text and the font are pure combinational logic; they do not know where the drawing is. Every cycle the renderer asks them with the current x, y, and they answer in the same cycle.

The same cell is asked many times. Along a pixel line, col changes only every 8 dots, and a character takes 8 pixel lines to finish, so each cell is asked 64 times per frame. Each time gx and gy differ and pick a different dot of the glyph. “Finish this cell” shows it best.

Each dot takes two bytes. lo = 0 sends pix[15:8], lo = 1 sends pix[7:0], and x advances only after the second byte.

Matching RTL: rtl/fpga/rtl/oled/oled_render.sv, oled_text.sv, oled_font.sv. The counter rules and bit selection on this page follow those modules; when the RTL changes, this page must be updated too.
